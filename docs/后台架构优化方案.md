# AI 造梦后台 · 架构优化方案（V1.0）

> 评估对象：`admin-web/`（React 后台）+ `cloudfunctions/adminApi`（后台接口）+ 相关云函数与 `web-app/`（新网站）
> 线上地址：https://makedream-admin.supersolo.tech/admin/index.html
> 评估日期：2026-08-17
> 结论先行：当前后台「能用，但地基不稳」。**存在 4 个 P0 级安全漏洞**，且后台仅覆盖「配置管理」，完全缺失「运营、监控、商业化、数据」四大能力。建议先止血安全漏洞，再做产品化架构重构。

---

## 一、执行摘要（TL;DR）

当前后台是一个 **1755 行单文件 React 组件** + **1620 行单文件云函数** 的「配置型后台」，只实现了 6 个标签页：模型、标签、图片、卡片、用户、设置。它解决的是「让运营改配置」，但距离一个真正的产品后台（`WEB_PRODUCT_PLAN.md` 第 4.2 / 8 节已明确规划）相差甚远。

**四个必须立刻处理的安全漏洞（P0）：**

| # | 漏洞 | 位置 | 后果 |
|---|------|------|------|
| 1 | **模型 API Key 泄露给客户端** | `cloudfunctions/modelConfig/index.js` `getList`/`getDetail` | 任何小程序用户可拿到所有生图服务商的 `api_key`，直接盗刷烧钱 |
| 2 | **模板/模型接口无鉴权即可增删改** | `modelConfig`、`featureConfig` 的 `create`/`update`/`delete` | 任何用户可篡改/删除全部模板与模型配置 |
| 3 | **积分可无限免费充值** | `cloudfunctions/points/index.js` `recharge` | 绕过支付直接 `recharge`，无限刷积分 |
| 4 | **开放注册 + 空表自封超管** | 登录页「创建后台账号」+ `bootstrapAdmin` | 任何人可注册；一旦 `admin_users` 被清空，可自封超级管理员 |

**结构性问题：** 后台没有 Dashboard、没有任务/故障中心、没有订单/退款、没有反馈管理、没有审计日志、没有数据分析，RBAC 形同虚设。

## 三、🔴 P0 安全漏洞（止血优先，1 天内可完成）

### 3.1 模型 API Key 泄露（最严重）

`cloudfunctions/modelConfig/index.js`：

```js
case 'getList':
  const res = await collection.get()        // ← 返回全部字段
  return { success: true, data: res.data }  // ← 含 api_key 明文
```

`ai_models` 集合里存的就是 `api_key: "pat_xxxxxx"` 明文。任何小程序端调用 `wx.cloud.callFunction({ name: 'modelConfig', data: { action: 'getList' } })` 即可拿到所有服务商密钥（Coze / supersolo / toapis / jiucan 等），被用于盗刷你的生图额度。

**修复：**
1. `modelConfig` 只保留读取白名单，且**过滤掉 `api_key`**（对照 `adminApi` 里 `sanitizeModel` 的做法）。
2. 更彻底：客户端读模型走 `featureConfig` 的脱敏字段即可，`modelConfig` 的 `getList/getDetail` 直接删除或加管理员鉴权。
3. 立即在云开发控制台**轮换所有已泄露的 API Key**。

### 3.2 模板/模型接口无鉴权可写

`featureConfig` 和 `modelConfig` 都暴露了 `create` / `update` / `delete` action，且**没有任何管理员校验**。任何用户可直接 `update` 篡改模板提示词、`delete` 删光模板。

**修复：** 删除这两个云函数里的写操作（客户端从不需要写模板/模型），或统一收口到 `adminApi`（已有 `requireAdmin` 鉴权）。

### 3.3 积分无限免费充值

`cloudfunctions/points/index.js`：

```js
async function rechargePoints(openid, amount, ...) {
  // 注释写着「暂时跳过支付，直接加积分」
  await db.collection(USER_COLLECTION).doc(openid).update({
    data: { points: _.inc(amount) }   // ← 无任何支付校验
  })
}
```

任何客户端调用 `points` with `{ action: 'recharge', amount: 999999 }` 即可免费加积分。

**修复：** 删除 `recharge` 作为客户端可直接调用的 action。充值的唯一入口应是 `paymentNotify`（支付回调，服务端验签后）触发，且走「预占 → 确认 → 释放」的账本模型（见 6.3）。

### 3.4 开放注册 + 空表白名单自封超管

- 登录页有「创建后台账号」按钮，`auth.signUp` 是**完全开放的**——任何人在公网都能注册后台账号。
- `bootstrapAdmin` 只要 `admin_users` 集合为空，就把「当前登录者」设为 `super_admin`。

**修复：**
1. 去掉登录页的注册入口（改为超管在后台「添加管理员」时创建账号，或注册后默认无权限）。
2. `bootstrapAdmin` 增加强校验（例如要求一个部署时注入的 `BOOTSTRAP_TOKEN`，或只在首个管理员创建时通过一次性密钥完成）。

### 3.5 其他安全隐患

| 隐患 | 位置 | 建议 |
|------|------|------|
| accessKey 硬编码在前端源码 | `admin-web/src/cloudbase.js` | 该 key 是匿名「PublishableKey」属可公开类型，但仍应从 `import.meta.env` 注入，不落库到 Git；且暴露了 env id |
| `virtualPayment`（虚拟/测试支付） | `cloudfunctions/virtualPayment` | 确认生产环境已禁用或删除，避免测试支付被当成真实支付 |
| `adminApi` 全表拉取 | `listGroups/listFeatures/listUsers` | 见 5.1，存在性能与超时风险 |
| 物理删除无审计 | 所有 `deleteDoc` | 见 4.4，改软删除 + 审计日志 |
| 积分调整非原子 | `adjustUserPoints` | 见 6.3，read-modify-write 存在竞态 |

## 四、目标后台产品架构（蓝图）

对照 `WEB_PRODUCT_PLAN.md`，一个产品化的后台应由「配置管理」升级为「运营 + 监控 + 商业化 + 数据」四合一。建议的模块结构：

```text
AI 造梦运营后台
├── 📊 运营概览（Dashboard）
│   ├─ 关键指标：今日生成 / 成功率 / 失败率 / 下载数 / 活跃用户 / 收入
│   ├─ 趋势图：生成量、失败量、成本、余额消耗
│   └─ 告警面板：Provider 健康、任务积压、异常退款
├── 🎨 模板中心
│   ├─ 模板库（搜索 / 多维筛选 / 批量上下架）
│   ├─ 模板编辑器（可视化字段编排、提示词变量、预览）
│   ├─ 调试与质量评测（测试用例集、多模型对比、评分门槛）
│   └─ 版本 / 灰度 / 发布（草稿→测试→审核→灰度→发布→下线）
├── 🖼️ 素材中心（现有「图片」模块升级）
├── 🧩 模型与路由
│   ├─ 模型配置（现有）+ 健康检查 + 成本统计
│   └─ 路由策略（主/备模型、熔断、灰度）
├── ⚙️ 生成任务与故障中心（重点补齐）
│   ├─ 任务列表（状态 / 模板 / 用户 / 模型 / 耗时 / 错误）
│   ├─ 失败定位（错误分类、Provider 响应、trace）
│   └─ 运维动作（手动重试、批量退款、卡死任务自愈）
├── 👥 用户 / 组织 / 权限（RBAC）
├── 💰 套餐 / 订单 / 余额 / 退款（重点补齐）
├── 📈 数据分析（模板漏斗、模型质量、成本毛利）
├── 🛡️ 内容安全与投诉（反馈、举报、封禁）
└── 🔐 系统配置与审计日志
```

### 4.1 与小程序 / 网站的关系重构

后台不再只是「改小程序配置」，而是统一管理三端：

- **统一用户体系**：建立 `userId`，小程序 OpenID 与网站账户解耦、可绑定（`WEB_PRODUCT_PLAN.md` 10.5 已定义）。
- **统一模板底座**：模板版本、分类、测试用例共用，小程序与网站各自保留适配层。
- **统一任务底座**：`generation_tasks` / `generation_history` 是三端共享，后台的「故障中心」直接读它。
- **统一账本**：积分迁移为只追加的 `credit_ledger`，兼容现有星光余额。

### 4.2 技术架构分层（摆脱单文件巨石）

```text
admin-web（前端）                     adminApi（云函数）
├─ pages/（Dashboard、模板、任务…）    ├─ 鉴权中间件（requireAdmin + RBAC）
├─ components/（可复用组件）           ├─ domains/（models、features、tasks…）
├─ features/（每模块一个目录）         │   ├─ 每个领域独立模块 + 字段白名单
├─ api/（统一请求层）                  │   └─ 业务校验 + 数据清洗
├─ store/（状态管理）                  ├─ lib/（分页、排序、审计、COS、账本）
└─ theme/（设计令牌 + 暗色主题）       └─ index.js（仅做 action 路由）
```

关键原则（继承自 `WEB_PRODUCT_PLAN.md` 10.1）：**云函数从「单个大入口按 action 分发」拆成清晰领域模块**；数据边界按 Identity / Template / Generation / Model Gateway / Billing / Analytics 拆开。

### P1 — 体验与数据（再做）

7. **路由化**：从 tab 切换改为 URL 路由（如 `/templates`、`/tasks`），支持深链接、刷新不丢状态、可分享。
8. **搜索与筛选**：模型/标签/卡片/用户/任务全量加搜索（关键词 + 状态 + 时间范围），而非只靠翻页。

12. **状态机升级**：模板发布状态从 `0/1` 二值升级为「草稿→待测试→待审核→灰度→已发布→已下线」。
13. **统一弹窗**：用自定义 Dialog/Drawer 替代遍地 `window.confirm`/`window.alert`，危险操作二次确认 + 输入名称确认。
14. **暗色主题**：长时间运营后台标配，按专家规范补 `light/dark/system` 三态切换。
15. **RBAC 落地**：角色 `super_admin / admin / template_editor / auditor / operator / finance / readonly_analyst`，`dispatch` 前按 action 校验角色权限。
16. **全表扫描改数据库分页**：`listGroups/listFeatures/listUsers` 现在是「拉全表 + 内存排序分页」，数据量大时超时且烧钱；改为 `where + orderBy + skip + limit`，并补索引（`_openid+createdAt`、`status+createdAt`）。
17. **数据字段归一化**：图片表存在 `modelCallId / model_call_id / modelCallIdSnapshot` 和 `generatedOpenid / generated_openid / openid / _openid` 多套字段名，做一次性数据迁移统一，删掉兼容分支。
18. **积分账本一致性**：`adjustUserPoints` 改为事务 + 原子 `_.inc`，并与 `points` 云函数共用同一套账本逻辑（当前是两套扣积分实现）。

## 六、关键数据与账本设计建议

### 6.1 模板版本化（当前最大产品短板）

当前 `ai_features` 是「原地改 + 草稿字段」，无法追溯历史、无法灰度。建议：

```text
templates（主表，稳定 identity）
template_versions（不可变版本快照）
template_placements（模板 ↔ 展示位 多对多）
template_test_cases（测试用例集）
```

发布后**不原地覆盖**，作品始终能追溯历史版本。

### 6.2 生成任务状态机

当前状态：`pending → running → succeeded / failed`。建议补齐：

```text
draft → validating → queued → running → post_processing → succeeded
                            ├─ retrying ──────────────┘
                            ├─ partially_succeeded
                            ├─ failed_refunded
                            └─ cancelled_refunded
```

要求：任务创建幂等（`idempotencyKey`，web-app 已实现）、Worker 用租约/锁认领、日志不泄露 API Key。

### 6.3 积分账本（预占 → 确认 → 释放）

当前 `points` 是「直接增减 + 事后写流水」，`adminApi.adjustUserPoints` 是「读-改-写」非原子。建议：

- 所有余额变化走**只追加的 `credit_ledger`**（不回写覆盖余额）。
- 扣费流程：**预占（reserve）→ 成功确认（capture）→ 失败释放（release）**，而非分散在多个函数手工补偿。
- 用 `runTransaction` + `_.inc` 保证原子性。
